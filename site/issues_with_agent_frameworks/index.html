    Issues with Agent Frameworks (and Why Raw Primitives Matter)¶

    Over the last few years, the ecosystem has exploded with agent and “orchestration” frameworks: LangChain, LlamaIndex, CrewAI, AutoGen, OpenAI’s Agents API, Google’s SDKs, and many more.

    They solve real problems, especially for demos and happy‑path use cases. But for many teams, the same abstractions that make “Hello World” easy become a constraint once you try to ship non‑trivial, production‑grade agents.

    This document summarizes the most common issues engineers and researchers run into with heavy agent frameworks.

    1. Hidden Control Flow (The Opaque Loop)¶

    Underneath almost every agent framework is the same simple pattern:
    an LLM in a loop, occasionally calling tools and updating state.

    Frameworks wrap this in high‑level constructs (AgentExecutor, “crews”, “graphs”) and expose a single .run() / .execute() entrypoint. The result:

    • Hard to answer basic questions:
    • “Why did it pick this tool?”
    • “Why did it loop again?”
    • “What exactly was in the prompt at step N?”
    • Debugging often requires:
    • custom callback handlers
    • vendor‑specific logging UIs
    • stepping through framework internals.

    When the loop is hidden, you don’t truly control the agent’s behavior, you configure it and hope the engine does the right thing.

    2. Rigid Abstractions Become a Cage¶

    Frameworks ship opinionated abstractions:

    • LangChain: Chains, Agents, Tools, Memory, Graphs.
    • CrewAI / AutoGen: Agents, Crews/Groups, Tasks, Managers.
    • Provider SDKs: “Agents” bound to a specific vendor’s tools, memory, and routing.

    These are great when your use case fits the intended patterns. But when you need something off the golden path, they become constraints:

    • Custom control logic (branching, retries, fallbacks) has to be expressed as:
    • nested chains
    • complicated task graphs
    • callbacks and hooks spread across many objects.
    • New research ideas (e.g., non‑standard tree search, unusual approval rules, domain‑specific heuristics) often don’t map cleanly to built‑in primitives.

    You end up “fighting the framework” instead of implementing the loop you actually want.

    3. Tooling Abstractions Leak in the Wrong Direction¶

    Most frameworks own the definition, routing, and execution of tools:

    • Tools are wrapped in framework‑specific classes or decorators.
    • Execution flows through a central executor or engine.
    • Error handling, retries, and serialization are baked into the framework.

    This creates several problems:

    • Tight coupling of your business logic to one framework’s tool model.
    • Difficulty handling nuanced cases:
    • fixing malformed tool arguments
    • recovering from partial failures
    • implementing complex dependency injection.
    • Hard to reuse tools outside the framework (e.g., in tests, CLIs, or other services).

    The “helpers” around tools often make simple things easy, but hard things harder.

    4. State and Memory Entangled with Execution¶

    Many frameworks blur the line between:

    • State – what has happened so far (messages, metadata, tool results).
    • Execution – what to do next (call LLM, pick tools, branch, stop).

    Common symptoms:

    • Conversation history is stored inside framework objects that are hard to snapshot, diff, or migrate.
    • Memory strategies (windowing, summarization, retrieval) are buried in agent classes instead of being swappable strategies.
    • Serializing or checkpointing agents for persistence or debugging is non‑trivial.

    When state and execution are entangled, you lose the ability to:

    • inspect or replay conversations cleanly
    • fork and merge branches easily
    • treat state as a first‑class artifact in your system.

    5. Difficult to Test and Reason About¶

    Because behavior is spread across:

    • configuration files
    • decorators and callbacks
    • runtime registries and global singletons

    …writing robust tests becomes painful:

    • Unit tests often have to mock large parts of the framework.
    • Integration tests require spinning up full “agent stacks”.
    • Simple questions like “what prompt did the model actually see?” are difficult to answer without special tracing tools.

    This makes it harder to:

    • catch regressions
    • iterate quickly on loop logic
    • trust agents in high‑impact or regulated environments.

    6. Vendor and Framework Lock‑In¶

    Some frameworks and SDKs are tightly coupled to specific providers:

    • Tool calling, memory, and control are exposed only through one vendor’s API surface.
    • Switching to another model family (or running local models) is a non‑trivial migration.

    Even “agnostic” frameworks can create lock‑in at a different layer:

    • Large frameworks define their own ecosystem of adapters, callbacks, and extensions.
    • Once your application logic is expressed in those abstractions, leaving the framework is expensive.

    This is especially problematic for teams that:

    • care about cost optimization across providers
    • need on‑prem or air‑gapped deployments
    • want to experiment with cutting‑edge open‑source models.

    7. Overhead and Operational Complexity¶

    Full‑stack agent frameworks often bring:

    • complex dependency graphs
    • custom CLIs and configuration systems
    • heavy runtime features (tracing, dashboards, hosted orchestration).

    These are valuable at scale, but they also:

    • increase cold‑start complexity (“I just want to run a loop.”)
    • limit where and how you can deploy (e.g., serverless, small services)
    • make it harder to understand performance and cost at a low level.

    For many teams, this is more infrastructure than they actually need just to run a handful of thoughtful loops around an LLM.

    8. Misalignment with Real‑World Agent Needs¶

    Production agents rarely follow the clean, linear loops shown in docs. They need:

    • dynamic system prompts based on user, org, or environment
    • special handling when tools are misused or unavailable
    • background detours and asynchronous side‑effects
    • custom guardrails, approvals, and audit trails.

    These “messy but necessary” behaviors are exactly where heavy frameworks struggle:

    • It’s hard to express bespoke orchestration rules within fixed agent types.
    • Many frameworks assume a small set of canonically “good” loop patterns.
    • Workarounds often involve bypassing the framework or patching internal APIs.

    In other words: the more unique and product‑specific your agent needs to be, the more likely the framework will get in your way.

    Why Raw Primitives and Explicit Loops Are a Better Fit for Many Teams¶

    The alternative to heavy frameworks is not “do everything from scratch.”
    It’s to use small, sharp primitives for:

    • talking to models (LLM client)
    • managing state (conversation / messages)
    • defining and executing tools
    • orchestrating via explicit loops

    …and to keep the main loop as normal, testable Python.

    This approach gives you:

    • Full visibility into every step.
    • The ability to inject arbitrary logic, metrics, and safety checks.
    • Easy snapshotting, branching, and replay.
    • Independence from any one vendor, framework, or “agent pattern.”

    Frameworks can still be useful on top of these primitives, but the core of your system stays simple, inspectable, and under your control.
